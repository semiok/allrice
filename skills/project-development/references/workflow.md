# 从需求到可用项目

## 需求与基线

把需求转成可检查的行为：谁使用、输入是什么、成功输出是什么、错误如何展示。优先交付用户真正需要的最小功能。不要未经要求加入账号、远端发布、收费依赖或外部数据服务。

新项目用 `workspace_project` 的 `open` 保存源码与锁文件。项目在每个 Run 中需要打开一次：新一轮继续已有项目时，先从当前会话和工具回执取得上一版完整 `project` 引用，使用 `open` 的 `source` 传入该引用的 `snapshot`，恢复同一个 projectId；不要通过 `files` 重建另一个项目。以恢复返回的完整版本调用 `list`、`read` 或 `search` 检查，以上一版确切引用保留交付基线。这些读取不会修改项目。记录用户给定的原断言和第一次执行结果。引用包含 projectId、snapshot.kind、snapshot.id 和 snapshot.checksum，不能用源码摘要替换快照引用。

## 修改与执行

使用 `apply` 的 `expectedHead` 和实际文本修改提案。遇到版本冲突先重新读取；不要覆盖未知修改或猜测版本。apply 返回的新版本用于后续执行，旧版本保留作为基线。

每次 `execute` 和 `service_start` 都带对应版本的 `projectPreparation`：实际 projectId、sourceDigest、锁路径和锁 checksum；选择当前支持的固定包管理器版本和实际依赖，不猜包的地址或 SHA。离线、安装脚本及资源选择遵循项目需求和原工具约束。无依赖 Node 小工具可以使用 pnpm 10.33.3、空 packages、禁止安装脚本和离线准备。

执行命令只能在保存项目的受管目录中进行。普通配置最高 60 秒、512MiB、64个进程；只有明确的 Web 开发配置才使用既有更大限制。工具拒绝不代表模型或项目已运行。原工具返回的实际选择决定本地或云端，不另做手工重试调度。

原测试失败时保留错误，定位后修改实现，再运行相同断言。不要为了通过而删断言、更改期望、返回伪造日志或把旧版本成功当作新版本证据。构建命令须真实生成文件；收集成果时声明精确路径与原工具支持的输出格式。工具返回终态成功、输出通过校验后，才报告文件已生成。

## 实际预览与续办

### 集中验证，减少重复启动

在同一个源码版本上，把独立的构建和原断言集中在一次 `execute` 中顺序执行，失败即停止并保留原错误。先完成这些确定性检查，再做实际浏览器交互。不要为每条断言重新打开项目、安装依赖或启动浏览器。工具回执的 workflowBudget.used / remaining / expiresAt 来自平台实际记录；失败的执行选择也会计数，重放同一调用不重复计数。每轮仍限 8 次执行、3 次修改、30 分钟；最后至少预留一次构建和一次必要预览，不用猜测剩余额度。

工具列表中有 `browser_workspace` 时，使用它实际提供的参数验证已保存的 HTML 或预览。静态 HTML 的 `verify` 支持一个 plan 中顺序执行 1–16 个步骤（`click`、`fill`、`text_contains`、`title_equals`），并且至少有一个文字或标题断言；把同一路径的输入、操作和断言放在一个 plan，超过上限再拆分。不要把静态 HTML 专用参数套到实时服务或普通浏览动作上。具体调用如下，变量必须替换成 execute 返回的真实 HTML 成果引用：

```json
{
  "command": "verify",
  "artifact": { "versionId": "$HTML_VERSION_ID", "checksum": "$HTML_CHECKSUM" },
  "plan": {
    "version": 1,
    "steps": [
      {
        "type": "fill",
        "selector": { "tag": "input", "label": "事项" },
        "value": "示例"
      },
      { "type": "click", "selector": { "tag": "button", "label": "保存" } },
      { "type": "text_contains", "expected": "已保存" }
    ]
  }
}
```

selector 只接受 tag 和精确、唯一的 label，不接受 id、CSS、exact；fill 只支持 input/textarea。每次 verify 是新隔离页面，不能假定上次输入和 localStorage 留存。open 接收实际获准 URL，不能传 artifact 或 plan；不能把 serviceId 当 HTML versionId，也没有 status/observe 命令。普通表单 label 与 aria-label 均可用于控件识别。当前有限验证计划没有原生确认框、下拉选择、reload 或设置 viewport 的动作；缺少必要动作时如实报告，不能编造命令或把模拟确认框当作实际确认。批量验证仍须检查每一步的回执，不能把部分完成当作全通过。

区分参数拒绝、页面未就绪、业务断言失败和执行连接错误：参数拒绝时只修正调用；已有成功的构建、截图、成果和未受影响的断言继续复用。布局有改动时保留桌面和手机检查；不要为了减少调用而省略它们。输出未知时先回读操作状态，不重复提交。

可交互项目通过 `service_start` 使用精确源码版本、明确监听地址/端口、健康路径和有限租期。用 `service_status` 回读状态，用户通过工作台该服务卡片的“打开预览”获取真实私有入口；不要编造工具动作、localhost 或访问地址。用户停止时使用 `service_stop`，确认真实状态，未确认回收时如实说明。

用户追加需求时继续同一项目，以刚刚交付的准确版本为基线。保留原测试与不受影响的行为，补充针对新要求的验证。源码修改后不能沿用旧预览作为新版本证明：按已有服务机制启动新版本，回读并提供对应入口；旧预览需要停止时仅停止本任务拥有的服务。不要为了运行同项目测试就先停掉仍可用的预览；云端有限构建可以与该预览并存。依赖锁不变的修改优先使用已有 apply + service_sync 更新同一服务，再用 service_status 核对真实源码摘要；依赖发生变化才按既有机制停旧服务并明确启动新版。最终交付前再次确认最新源码对应的预览仍就绪；不要为无关的补充测试重复构建完整项目或主动停止最终预览。

写操作结果未知时，先检查当前项目版本、操作状态、成果或服务，再决定下一步；不重复 apply、重建所有文件或生成同一成果。展示或下载脚本出错时复用已有 Run 和文件，只有确证的实现问题才修改源码。

版本、参数、权限和资源界限由程序校验。本说明不替代它们，不触发平台自主修复或发布。
