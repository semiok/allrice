# 从需求到可用项目

## 需求与基线

把需求转成可检查的行为：谁使用、输入是什么、成功输出是什么、错误如何展示。优先交付用户真正需要的最小功能。不要未经要求加入账号、远端发布、收费依赖或外部数据服务。

新项目用 `workspace_project` 的 `open` 保存源码与锁文件。已有项目从当前会话和工具回执取得完整 `project` 引用，再使用 `list`、`read` 或 `search` 检查；这些读取不会修改项目。记录用户给定的原断言和第一次执行结果。引用包含 projectId、snapshot.kind、snapshot.id 和 snapshot.checksum，不能用源码摘要替换快照引用。

## 修改与执行

使用 `apply` 的 `expectedHead` 和实际文本修改提案。遇到版本冲突先重新读取；不要覆盖未知修改或猜测版本。apply 返回的新版本用于后续执行，旧版本保留作为基线。

每次 `execute` 和 `service_start` 都带对应版本的 `projectPreparation`：实际 projectId、sourceDigest、锁路径和锁 checksum；选择当前支持的固定包管理器版本和实际依赖，不猜包的地址或 SHA。离线、安装脚本及资源选择遵循项目需求和原工具约束。无依赖 Node 小工具可以使用 pnpm 10.33.3、空 packages、禁止安装脚本和离线准备。

执行命令只能在保存项目的受管目录中进行。普通配置最高 60 秒、512MiB、64个进程；只有明确的 Web 开发配置才使用既有更大限制。工具拒绝不代表模型或项目已运行。原工具返回的实际选择决定本地或云端，不另做手工重试调度。

原测试失败时保留错误，定位后修改实现，再运行相同断言。不要为了通过而删断言、更改期望、返回伪造日志或把旧版本成功当作新版本证据。构建命令须真实生成文件；收集成果时声明精确路径与原工具支持的输出格式。工具返回终态成功、输出通过校验后，才报告文件已生成。

## 实际预览与续办

可交互项目通过 `service_start` 使用精确源码版本、明确监听地址/端口、健康路径和有限租期。用 `service_status` 回读状态，用户通过工作台该服务卡片的“打开预览”获取真实私有入口；不要编造工具动作、localhost 或访问地址。用户停止时使用 `service_stop`，确认真实状态，未确认回收时如实说明。

用户追加需求时继续同一项目，以刚刚交付的准确版本为基线。保留原测试与不受影响的行为，补充针对新要求的验证。源码修改后不能沿用旧预览作为新版本证明：按已有服务机制启动新版本，回读并提供对应入口；旧预览需要停止时仅停止本任务拥有的服务。

写操作结果未知时，先检查当前项目版本、操作状态、成果或服务，再决定下一步；不重复 apply、重建所有文件或生成同一成果。展示或下载脚本出错时复用已有 Run 和文件，只有确证的实现问题才修改源码。

版本、参数、权限和资源界限由程序校验。本说明不替代它们，不触发平台自主修复或发布。
