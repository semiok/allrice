2026-09-27，用户确认调整 huihuimac 上的沙箱资源，并在管理后台展示实际资源使用情况。

## 已调整的环境

- `allrice-b2` 没有运行或停止的容器，已停机；保留磁盘、配置和镜像。它仍是 Rice Bridge 本地命令沙箱，设备端准备环境时可按需恢复，并非删除废弃服务。
- `allrice-cloud-b4` 从 2 vCPU / 2 GiB 调整为 3 vCPU / 4 GiB。未更改默认 Docker context。
- Linux 实测内存 4,103,761,920 字节；系统预留 820,752,384 字节，Office 预览容器预算 805,306,368 字节。每个执行位置按 512 MiB 脚本 + 128 MiB 运行开销计算，得到 **3 个计算槽位**。
- 升级时先确认 Dev 任务、员工试用和操作租约均为空，暂停 Dev Web/Worker，再重启 VM。等待预览容器和本地 3112 转发恢复后重启 watchdog，使容量探测包含预览服务预算；最后恢复 Web/Worker。
- 宿主机 16 GiB RAM、8 个逻辑 CPU。停止 2 GiB 配额的空闲 VM 不等于归还 2 GiB 实际内存，不能承诺扩容后零新增占用或排队只需 1～2 秒。

## 后台入口与事实来源

管理后台 → 平台设置 → 运行技术详情：顶部新增“云端计算 · 使用 / 槽位”和“等待计算 / 数据库阻塞”，下方“运维资源”展开显示：

- 云端实际 CPU、内存总量、可用内存、系统预留、其他服务预算、运行容器与计算槽位。
- Worker 所在系统、有效 CPU/内存、当前可用内存、Worker RSS、启动时计算的任务并发上限。
- 全局进行中/待领取任务、等待计算/执行中请求、最长待领取时间、数据库锁等待与采样时间。

Worker 复用 MET-162 每 30 秒的压力采样和已有 watchdog，只将资源元数据写入 `allrice_runtime_metadata`，不增加服务、依赖或数据库迁移。历史样本继续落在现有 `diagnostics/<workerId>/pressure.jsonl`（8 段 × 5 MB，停用 Worker 目录 7 天清理）。多个 Worker 共用同一物理后端时，前端按 `backendId` 去重容量；全局队列快照不累加。

超过 90 秒未上报视为离线，展示最后采样时间并从实时汇总排除。探测失败、旧 Worker 未上报或诊断数据库失败显示未知，不伪造为 0。停机时删除本进程报告；历史报告读取限最近 7 天。Web 仅读数据库，平台管理员认证后才能获取运维数据，响应禁止缓存。公司/员工筛选不改变这些平台资源总量。

托管计算目标的 `concurrency_limit` 原先固定为 2；现同步使用探测到的 `profile.maximumConcurrency`，扩容后的物理容量与登记信息一致。租户权限、商业配额、1 小时有效任务时限不因本次扩容而改变。
