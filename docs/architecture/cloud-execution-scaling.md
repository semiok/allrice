# MET-162：云端执行稳定性一期

2026-09-27 用户确认：第一阶段以 **20 个独立租户、每个租户至少 1 名员工同时处理任务** 为目标；后台必须记录排队与阻塞情况，作为后续优化依据。

本描述替代此前 5 个 PR、沙箱服务迁移及多节点扩展的交付方案。用户已授权按两个 PR 顺序实施，现开始 PR1；代码正在本地验证，尚未合并或部署，20 租户实测尚未通过前不计作已交付。

## 交付结果

- 20 个租户同时提交后，多个员工能并行推进模型请求、查询和工具调用；不能因为某个长任务占满单一 Worker 槽位，使其他所有任务串行等待。
- Office 与通用云端计算共享资源调度。容量满时进入可取消、可恢复的等待状态，前台显示“等待计算资源”；正常满载不再以 `cloud_capacity_unavailable` 结束任务。
- 算力按实际机器资源分配。20 个租户同时工作允许计算步骤公平排队，不要求同时启动 20 个 Office 容器。不能把“20 个请求已入队”当成“20 个租户持续工作”的全部验收证据。
- 后台能够回答：谁在等、等在哪里、为什么等、等了多久、当前资源是否用满、何时恢复推进。
- 已知的内部用量拦截与数据库锁顺序问题不再让正常任务失败。真实模型服务故障、脚本错误、取消、超时仍如实呈现，不能用隐藏错误或仅凭文件存在来判定成功。

这是实施与验收目标，尚未证明当前 Dev 已能流畅承载 20 租户。

## 当前依据与瓶颈

2026-09-27 只读核对：

1. **Worker 主任务并发为 1**：源码及 Compose 默认 `ALLRICE_WORKER_CONCURRENCY=1`，Dev 最近启动日志也为 1。必须同时处理主任务调度；仅增加沙箱位置不够。
2. **执行 VM 为 2 vCPU / 约 2GiB**：Office 单容器限制为 1 vCPU / 512MiB，共享 2 个物理执行位置。512MiB 是上限，不能等同于每个空闲容器实时占用。
3. **容量判断分散**：数据库准入、契约、Docker 后端、watchdog 与目标登记包含固定容量。Office 底层已有等待，而部分通用计算路径仍提前报满载；需要统一事实来源。
4. **排队与执行计时混在一起**：Office 当前的 60 秒操作期限包含资源等待；watchdog 还有独立期限。长队列不能提前耗尽尚未开始执行的脚本时间。
5. **数据库问题独立存在**：[PR #149](https://github.com/semiok/allrice/pull/149) 已包含已定位的成果发布锁顺序修复。实施前核对其实际合并/部署情况，复用修复并补并发验收。

沙箱 VM 的配置不代表 Web、数据库和 Worker 所在机器的全部资源。验收必须记录两侧配置以及模型服务的实际并发能力。

## 本期实现边界

### 1. 主任务与沙箱分开调度

- 复用现有 PostgreSQL 队列、租约、任务时钟和 DSH 原生执行机制，分别管理主任务推进与物理沙箱占用。
- 调整 Worker 并发策略，避免默认 1 造成全局串行；依据 Worker 实际资源和连接池能力给出有界并发，不能简单无限放开，也不能机械地等同于沙箱数量。
- 20 个租户均能获得推进机会；一个租户的批量导出、子助手或慢请求不能长期占满全部资源。优先在现有队列领取处实现基本公平性，不另造调度平台。
- 资源领取、状态更新使用短事务；等待、模型请求、文件生成和外部 IO 放在事务外。等待任务保留心跳/恢复与取消能力，避免占满全部推进位置。

### 2. 单机自动容量

- 启动时读取**实际执行沙箱的 Linux/VM** 有效 CPU、内存及已施加的资源限制，扣除系统和同机服务预留，再按现有任务资源需求生成保守容量。
- 同一套部署默认值适配不同服务器；扩容后重启自动重算，无需逐文件修改并发数。管理员可选设上限，正常部署不要求手工计算容量。
- 不使用强制至少 2 个并发的公式；资源只够 1 个就运行 1 个，一个也容纳不了就报告环境资源不足。
- 调度器、执行后端和 watchdog 共用同一容量结果；启动中、执行中及预热实例均纳入预算。增加 Worker 不能凭空增加同一机器的物理容量。
- 本期仅做启动计算和运行时基本内存压力保护：压力高则暂停新领取，资源恢复后继续。保留健康在途任务，不做自动扩容、复杂调谐或多节点调度。
- 旧租约不等于资源释放；确认进程已结束/被终止并清理后才能释放占位。

### 3. 保留 1 小时，用量仅统计

- 默认单任务 1 小时保持，沿用任务权威时钟的运行/等待规则；平台排队与实际执行分别计时，不让资源等待耗尽单次脚本执行期限，也不误判为死循环。
- 移除执行过程中的累计 Token、模型/工具调用次数及费用拦截，覆盖 API、订阅、父任务、子助手和原生压实。
- 用量与费用继续真实记录；缺失统计或价格记未知，不因统计未知将已实际完成的任务判失败。真实执行结果不明、未结束子任务或外部副作用未知仍需核对。
- 保留无进展/死循环保护、用户取消、物理资源限制和协议约束。未来按租户任务次数或使用天数计费在新任务入口处理，本期不新建商业套餐体系。

### 4. 数据库并发收尾

- 复用 #149，复核本次涉及路径的锁顺序，补成果发布、任务时钟、租约恢复及取消并发回归。
- 对确认回滚的 `40P01` / `40001` 有限重试完整短事务，沿用幂等键；不盲目重放已经发生或结果未知的外部写入。
- 仅针对实测慢事务/锁等待做修复，不全仓移除锁，不另建事件系统，不预先引入 outbox、Redis 或工作流平台。

## 后台日志与诊断：PR1 必须交付

复用现有任务事件、操作账本和服务日志，增加结构化诊断字段；不另外建设一套监控平台。日志须落盘/持久保存并配置轮转与明确保留期，不能仅存在浏览器或进程内。

### 关联与事件

- 关联字段：`tenantId`、员工/派驻标识、`runId`、`jobId`、父任务标识、`operationId`、`workerId`、执行节点/容器标识；未分配的字段允许为空。
- 记录时间、当前阶段、进入/离开等待、领取资源、启动/执行/交付/清理、完成/失败、取消/恢复；状态转换和日志重复需可识别。
- 等待原因分开记录：Worker 容量、沙箱容量、内存压力、模型服务并发/限流、数据库连接池、数据库锁等待、用户授权/输入。原因未知就记未知，不把所有延迟归为沙箱繁忙。
- 记录每段及累计等待时长、执行时长、首次领取时间、最近实际进展、重试次数、规范化错误码。正常排队、慢操作与真实停滞分别呈现。
- 数据库锁问题保留可关联的等待时长、阻塞会话/事务标识和 SQLSTATE；对慢等待按阈值采样，不记录完整 SQL 参数、凭据、提示词、文档正文或模型推理内容。

### 容量与后台呈现

- 启动时记录探测到的资源、预留量、计算容量和配置版本；状态变化或低频汇总时记录 Worker 活跃/等待、沙箱启动/执行/预热/等待、最长等待、内存压力及进程清理结果。
- 在现有后台运行详情中展示当前阶段、排队时长、等待原因、最近进展与诊断日志入口；可按租户、Run、时间和原因检索。不单独重做管理后台。
- 汇总任务成功/失败/取消、排队和执行耗时 P50/P95、最长等待、吞吐、按原因统计的等待、死锁/重试次数。既记录成功结束，也保留最终失败及长等待证据，避免统计只包含成功样本。
- 每 200ms 轮询不重复写相同日志；以状态变化和限频采样记录，日志故障不能反过来终止正常业务。

## PR 拆分：两个 PR，稳定性优先

### PR1：20 租户并发推进、自动容量、满载排队与诊断

交付上述主任务/沙箱调度、启动容量探测、用量仅统计、已定位数据库修复，以及后台日志和最小诊断入口。保留 1 小时、取消、恢复与无进展保护。先用现有 Docker/gVisor + DSH 原生 Office 完成 20 租户验收。

### PR2：按实测瓶颈优化启动性能（条件项）

PR1 的日志证明容器/依赖冷启动是明显瓶颈后，才在现有后端增加小型纯净预热池。池规模按资源预算计算，可为 0；不固定常驻 2～3 个。

预热只含公共依赖，领取后绑定任务，用后销毁；处理空闲期限、领取后的执行期限、补位、重启核对和清理失败。与相同工作负载的冷启动基线比较收益。若瓶颈主要是模型服务或文件转换，则记录证据，不为完成 PR 数量硬做池；优化范围依据证据再调整。

20 租户稳定工作不以预热池为前置条件。若无需 PR2，记录结论即可，本 MET 不因未做预热而长期悬挂。

## 第一阶段验收

### 工作负载与测量

1. **20 个独立租户，各至少 1 个员工**，同一时间窗口发起真实任务；以下两个场景各完成一轮，故障修复后复测受影响场景。记录应用 SHA、部署资源、计算容量、模型路由、工作负载和测试窗口。不能用单租户 20 个请求或仅建立 20 条连接替代。
2. 混合场景：10 个查询/分析任务 + 10 个 Office 任务，Office 交付 Word/Excel/PPT。证明多个主任务在重叠时间推进，轻任务不被长导出整体堵住。
3. 集中计算场景：20 个租户同时生成 Office 三格式，验证有限位置持续出队、公平推进和文件交付；不要求 20 个容器同时运行。
4. 每轮输出每租户开始/领取/完成时间、各段等待与原因、成功/失败结果，并汇总 P50/P95、最长等待和吞吐。首轮建立等待时间基线；没有实测前不承诺秒级响应，报告必须说明哪些等待会影响可接受体验。

### 通过条件

- 每个租户有可追踪状态和推进机会；资源释放后持续领取等待任务，没有长期被其他租户挤占的任务，没有全局单任务串行。
- 验收工作负载不因内部容量满、累计用量限制、已定位锁顺序问题失败；不发生超分配导致的 OOM、重复交付或跨租户数据混用。
- 真实模型/外部服务故障单列，保留失败证据并验证恢复；不能把失败剔除后宣称 20 租户验收通过，受影响场景需补测。
- 等待中取消、执行中取消、Worker 重启恢复、残留容器清理通过；平台等待不误触发无进展保护或耗尽脚本执行时间，默认 1 小时规则有回归验证。
- 三格式文件可下载，已有侧栏预览正常；真实未完成不会被伪装为成功，统计未知不会覆盖实际完成状态。
- 只看后台诊断即可定位某个任务是在等待 Worker、沙箱、模型服务还是数据库；重启后仍可查询验收窗口的日志。
- 当前 2 核/2GiB 执行环境实测；启动容量算法使用小内存和更大内存资源样本验证同一配置自动算出合理上限。没有实机验证的规格明确标为模拟，不把建设多台服务器作为本期前置条件。

## PR1 实现与部署说明

- Worker 默认 `ALLRICE_WORKER_CONCURRENCY=auto`，按 Worker 所在机器可用内存、CPU 计算推进槽位，最大 32；继续复用 PostgreSQL 的租户公平领取。Worker 数据库池为 10 条连接，诊断另用一条有超时的只读查询连接。
- Docker 后端从独立 watchdog v2 读取启动容量。每个计算任务预算 512MiB 加 128MiB 运行时开销，预留至少 512MiB/20% 系统内存，并扣除同 VM 常驻服务内存；允许容量为 0。低可用内存暂停新领取，已有健康任务不因压力重新计算容量。
- 实机探测：2 CPU、2,061,242,368 bytes VM，Office 预览服务内存上限 768MiB。按上述保守预算只够 **1 个计算槽位**。无此预览服务的 2GiB 模拟样本是 2 个；不能把它冒充当前部署容量。20 租户同时工作依靠并行模型阶段和公平计算排队，不代表 20 个容器。
- 同一 Docker daemon 通过原子容器名称预留槽位，跨 Worker 共用物理容量。占位过期仍须确认实际计算进程已停止，旧持有者再次执行前校验原容器身份。
- 迁移 `0116_execution_resource_waits.sql` 保存可恢复的等待投影；状态转换复用 `allrice_audit_events`。任务时钟识别等待，其他并行模型/工具仍计有效执行时间。Office 内层脚本仍为 60 秒，外层 DSH 等待期限延长，默认有效执行一小时保持。
- 现有后台运行详情增加排队/执行/最近进展与诊断列表。服务压力日志每 30 秒采样，单 Worker 最多 8 × 5MB，旧 Worker 日志目录七天后清理；任务诊断随现有数据库审计记录保留，不新增自动删除审计历史。
- 部署时先验证 idle，再配套切换 watchdog v2 与 Web/Worker；新 Worker 不能搭配旧 watchdog。先保留旧脚本用于回滚。迁移是增量表，不改写历史任务冻结快照。
- PR2 仅在完成 PR1 实测后依据启动/执行耗时推进。资源不足时不预热，不在 2GiB VM 上固定常驻多个计算实例。
