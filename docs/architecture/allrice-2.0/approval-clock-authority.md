# M5 补测修正：审批时间使用服务器权威时钟

2026-09-08，B3 后补测；代码待提交，不表示已部署或启用租户权限。

## 实际问题

M5 系统时间约快于数据库宿主 1.4 秒。浏览器生成的 `respondedAt` 被直接送进严格的交互匹配函数，
该函数要求时间落在请求创建与服务器当前时间之间。因此身份、版本和操作完全匹配的有效批准也可能报
`approval_response_mismatch`。同机测试未暴露这一缺陷；跨机器 Chrome / PostgreSQL 验收复现。

## 修正与边界

- `decideRuntimeActionApproval` 仍先做 schema 验证、配置及身份检查、锁定精确审批行。
- 首次有效响应在事务内以 PostgreSQL `clock_timestamp()` 标记 `respondedAt` 和 `decided_at`。
  客户端报告时间不具有授权效力；不更改电脑时钟、不增加授权有效期，也不引入任意“宽容几分钟”。
- 请求身份、task/attempt、租户、respondent、requestDigest、version 和 decision 继续精确匹配。
- 重试复用首次接受时间，再逐字段比较响应 ID、身份与决定；不会重复决定、再次消费或延长授权。
  客户端时间不参与重试冲突判定；首次服务器接受时间保持不变。
- 过期/撤销/配置变化/底层授权变化仍在数据库时间下拒绝，批准结束写入后仍复检期限。
- 不更改纯契约层对可信时间的严格校验；仅在服务端将不可信的浏览器输入转换为权威响应。
- 无数据库迁移；既有已接受响应兼容，不批量改写历史审批。

新增数据库回归覆盖客户端快/慢一天、原响应重试、决定篡改、防双消费、撤销后重试与已过期请求。
跨机器闭环及完整结果另见 M5 补充验收记录。新代码尚未替换 Dev 运行 release，不能把源码通过写成已上线。
