# MET-161：组织、员工账号与统一工作台

工单：https://linear.app/metasnowsky/issue/MET-161

按 PR1 → PR6 顺序实施。每个 PR 独立验证；全部完成后，核对当时 Dev 的实际发布版本及其他工作分支，统一集成部署一次。单个 PR 完成不触发 Dev 部署。

## 交付拆分

1. 统一登录：数据库用户名、会话与密码生命周期；统一域名不再绑定 Snow。
2. 组织和员工管理：公司、默认工作区、普通员工账号、岗位职能、批量导入、密码重置与停用。
3. AI 员工配发与人设：组织默认名单、按人批量增删、持久化个人撤回、按公司与当前员工注入上下文。
4. 全局 AI 发布：编辑 AI 本身，更新所有已配发对象；保留运行中版本快照和真实更新回执。
5. 工作动态：按公司、员工、AI 员工查看真实运行、等待、失败与交付成果。
6. 迁移和验收：旧域名、设备接口、现有身份与资料迁移，最终联合发布。

不依赖 MET-145、MET-146 或 Team 新能力。

## PR1：统一账号身份

- `allrice.bplabs.xyz` 和默认本地入口使用数据库账号登录。登录名是全局唯一、不区分大小写的英文昵称；显示名可以独立修改。已有邮箱登录兼容保留。
- 公司和工作区来自账号当前有效成员关系，不能通过域名或客户端传入的公司 ID 越权。多个历史工作区继续由已有成员关系检查。
- 员工统一从 `https://allrice.bplabs.xyz` 登录；管理员独立从 `https://allrice-admin.bplabs.xyz` 登录。按服务器平台身份校验入口，管理员账号不能登录员工入口，旧管理员会话也不能在员工入口调用接口；员工不能登录管理后台。租户设置中不再显示管理平台菜单。
- 接受管理员指定的初始密码 `admin@321`。存储继续使用随机盐 scrypt，不把明文密码写入账号表或日志。新员工创建在 PR2 提供，现有账号批量迁移在 PR6 执行。
- 用户可以在「设置 → 账号与用量 → 修改登录密码」主动改密，不增加首次登录强制改密步骤。改密撤销所有旧登录会话。
- 登录校验、创建会话和改密在用户行锁下串行化，避免重置密码期间旧密码创建仍有效的会话。
- 旧 Snow、Drink 导航跳到员工入口，旧 `allrice-dsh` 后台导航跳到 `allrice-admin.bplabs.xyz`；设备、回调等 API 保留原地址兼容。仅未迁移的账号首次通过原部署凭证登录时初始化用户名和数据库密码；已迁移账号一律使用数据库密码，重复初始化不会覆盖密码或恢复撤销的成员关系。
- 旧入口签名的用户 ID 必须与数据库会话一致。Bridge 设备接口保持原有独立凭证验证路径。
- 增量迁移为 `0113_unified_login.sql`；`0112` 留给正在并行开发的会话引用功能。

验证使用随机 PostgreSQL schema 和合成员工，无真实租户、模型调用或 Dev 修改。覆盖共用入口、跨公司隔离、平台权限独立、账号停用/撤销、用户名唯一、改密与并发登录、旧入口迁移幂等及改密接口。

## PR2：组织与员工账号管理

- 后台「组织管理」新建公司时自动生成默认工作区，不再要求填写公司 slug、域名或邮箱。
- 员工基础资料按公司保存：姓名、岗位、职能。同一历史用户在不同公司的资料互不覆盖；AI 模板不因新增公司或员工而复制。
- 单个创建和表格批量导入共用账号服务。新账号直接激活为普通员工，默认密码为 `admin@321`；后台可指定初始密码，员工可主动改密。
- 可从 Excel 粘贴英文账号、姓名、岗位、职能四列，一次最多 100 人。导入原子提交，重名或校验错误时整批不写入，不通过 upsert 接管其他账号或重置其密码。
- 兼容现有 email 非空约束：无邮箱的新员工使用不可投递的内部唯一占位值，不对用户展示、不用于平台管理员识别或通知。
- 管理员可编辑员工资料、重置密码、停用/启用账号。停用是账号级登录停用，保留既有公司成员关系、会话、文件及历史；重置和停用撤销旧登录，重新启用不会恢复旧会话。公司基础资料和员工编辑具备并发版本检查。
- 历史多工作区的 AI 配发、应用、电脑和用量沿用已有管理组件，工作区选择仅在确实存在多个工作区时显示。按人批量 AI 配发由 PR3 替换完善。
- 管理接口逐次核验真实平台管理员与当前数据库会话；跨域写入被拒绝。员工账号界面不能重置或停用平台管理账号。

验证覆盖真实 Chromium → HTTP → 随机 PostgreSQL schema 的公司创建、员工开户、表格导入、编辑、改密、停用/启用及越权拒绝；另测导入原子性、公司人设隔离、过期编辑冲突和审计不含密码。

## PR3：按人配发与任务人设

- 公司默认 AI 名单可在招聘员工之前配置，后续新增普通员工直接继承。新公司未配发 AI 时不再自动创建 Rice。
- 员工列表支持单人、勾选多人、姓名/账号/岗位筛选结果、全公司四种范围。管理员可添加、移除或恢复跟随公司默认；实际命中人数与变更人数分别返回。
- 在现有 `allrice_employee_assignments` 上保存 `inherit/include/exclude`；公司默认开关保存在现有部署记录。个人明确添加或移除不被心跳、成员同步或 AI 更新覆盖；不会按人复制 AI 定义或增加平行授权表。
- 移除配发请求取消相关未结束任务，保留已有工作记录和文件。回执区分“已请求停止”和任务实际结束。旧会话也无法绕过已撤回配发创建新任务。
- 全公司撤回后仅给部分人员重新配发时，不自动恢复其他人的旧配发。后台旧入口归档 AI 也同步撤回公司部署，避免后续发布意外恢复。
- 创建 Run 时冻结公司名称、业务背景及当前员工姓名、岗位、职能；通过现有 DSH 内核指令输入装载。资料修改从下一次 Run 生效，运行中、重试和恢复继续使用原快照。上下文校验和包含人设，避免原生会话继续使用过期资料。
- 配发写入与现有发布共用锁顺序，检查部署版本，拒绝过期编辑；按数据库实际公司成员解析目标，不能传入另一公司的用户 ID。

验证覆盖个人例外与公司默认组合、空公司预配发、新人继承、心跳/发布后撤回保持、稳定配发 ID、任务取消请求及历史保留、人设冻结、并发冲突，以及 Chromium 中勾选配发→移除→公司默认→恢复继承的完整链路。

## PR4：全量发布与真实回执

- 接入 PR #155 已完成的员工编辑器和草稿测试调整，继续复用现有不可变运行包与物化链路。AI 发布页移除公司/工作区勾选；草稿测试使用的环境不再带入发布范围。
- 「保存草稿」只更新草稿；「更新到租户」保存当前修改并更新全部现有有效部署。首次发布没有配发时只进入 AI 目录，随后从组织管理配发。
- 新管理界面使用 `scope: assigned`，数据库在员工锁下查询实际部署；不扫描全体工作区，不接管个人增删。旧显式目标参数仅为既有受控引导/兼容调用保留。
- 所有目标在同一个数据库事务中更新。若某家公司失败，整批零更新，原正式版本、配发和版本指针均保持，失败回执说明公司并写入现有审计。修复后再次点击更新重试；不会将部分更新显示为全部成功。
- 成功回执按实际更新部署汇总公司数、有效员工数和公司明细；无成员的默认名单也能升级，人数显示为零。回执持久保存到现有发布审计，无平行发布账本。
- 现有会话下一轮使用新员工版本；运行中、等待恢复与重试不更换冻结运行包。个人明确移除、公司暂停及已撤销连接不会被更新恢复。新增加的工具仍按默认开放规则配置。
- 回退也从实际配发关系推导范围，并允许只回退未配发的目录版本。发布/撤回/配发共用锁顺序；若预检后范围或策略改变，明确要求重新读取，不按旧页面覆盖。

验证：两公司全量更新、旧会话下一轮与在途 Run 版本隔离、个人排除与回退、真实 SQL 写入故障触发整批回退和重试、预检后撤回、空配发回退、显式暂停保持。完整后台 Chromium 集成 15 项通过，保留 #155 的技能工具联动和草稿导航回归。

## PR5：公司和员工工作动态

- 后台主导航收敛为「组织管理 / AI 员工 / 工作动态 / 平台设置」。工作动态按公司 → 员工 → AI 员工及工作 → 交付文件展开；版本、模型、运行技术详情和反馈归入平台设置。旧技术详情链接继续可用。
- 公司和员工展示当前进行、排队、等待，以及最近 7 天完成/失败/取消数量；具体员工的工作列表保留全部历史并按游标翻页。电脑和应用数量读取实际未撤销设备与有效成员连接，分别按公司及使用者统计。
- 状态来自现有 Run、任务权威时钟与等待记录；进展只采用 DSH 可公开事件标题，等待原因区分员工回复、暂无进展、电脑连接和外部操作。不生成虚假百分比、第二套计时或日志。
- 复用已有任务检查、Office/文本预览和存储读取；文件可直接下载。默认收起版本 ID、操作账本和技术参数；停用员工后仍允许平台管理员查看其原有工作和文件，执行与配置授权不随之放开。
- 支持员工搜索、需关注筛选、AI 员工和状态筛选；列表自动更新可关闭，后台页暂停自动更新。刷新保留已经加载的页、所选员工、工作详情和展开的预览，不清空闪屏。
- 查看和下载均检查当前平台身份及精确公司、工作区、使用者、Run、文件归属，文件读取后再次检查。技术详情和摘要沿用现有脱敏，不输出凭证和隐藏推理。

验证：真实 PostgreSQL 状态/时间投影只读、历史统计、停用后查看、越权与过期身份拒绝、相同时间戳分页、归档排除；Chromium 逐层查看、预览/下载、连续刷新保留展开状态及拒绝跨公司文件。既有 15 项后台浏览器行为回归通过。

运行技术详情同样按「公司 → 真实员工 → Session / Runtime」浏览：公司按组织 ID 合并为紧凑一级选择栏，员工列表复用组织成员接口（含尚无会话的员工），二级选择后仅加载该公司、该员工的 Runtime 和 Bridge。数据库先按公司与 owner 过滤，再限制列表数量；会话统计和设备心跳也按 owner 汇总。切换层级取消旧请求，自动刷新保留选择，避免展示前一个员工的事件与设备。Run 按最新轮次在前展示，保留原轮次编号；默认只展开最新 Run，其他轮次折叠，手动展开/收起在刷新时保留。

## PR6：入口切换与旧账号迁移

- 正式使用 `https://allrice.bplabs.xyz`，登录后按账号有效成员关系进入工作台；后台试用链接也统一使用此入口，适用于新增公司。
- 旧 Snow、Drink 的页面 GET/HEAD 转到 `allrice.bplabs.xyz`，旧 Allrice 后台入口转到 `allrice-admin.bplabs.xyz`，保留安全的路径和查询参数；仅固定已知域名及页面路径参与迁移。Bridge 配对、心跳、回执、浏览器设备接口、SSE、OAuth 回调、签名下载及静态资源继续留在原域名，由原处理器验证，避免设备被网页重定向打断。独立 DSH 管理站点不在此范围。
- 员工登录保留工作与应用设置深链接；后台深链接只由管理员入口恢复。两个入口的 Cookie 各自绑定域名，使用 HttpOnly + SameSite=Lax，配合现有 OAuth 的用户绑定、15 分钟有效期和单次 state 校验，支持应用登录后的跨站顶层 GET 回调。旧的进行中 OAuth 仍走原回调；已退出旧站点的用户从新入口重新发起应用登录，已连接应用凭证和绑定不迁移或重建。
- `pnpm identity:migrate-portals` 默认预览，`--apply` 才在同一事务提交。默认读取部署中 Snow、Drink 和平台管理员的原有账号映射；其他旧账号可提供私有 `--manifest=/path/accounts.json`。不根据昵称猜公司，不创建替代用户/工作区。
- 仅用户名尚未初始化的普通员工设初始密码 `admin@321`；平台管理员使用原部署管理员凭证，绝不使用员工默认密码。已初始化账号保留用户名与密码，停用账号不启用，撤销的成员关系不恢复。用户名冲突、原身份缺失或管理员类型不符时整批回滚，输出不含密码/哈希。
- 保留公司、用户、工作区、配发、会话、文件、订阅和设备 ID。历史公司切换为管理员维护 AI 名单，已有资料、个人配发例外和暂停配置不被覆盖。密码初始化撤销旧登录，员工到统一入口重新登录。

### 联合发布步骤

1. PR1–PR6 全部通过检查后，读取 Dev 当前实际版本与验收状态；从其提交建立独立发布工作区，整合最终主干，检查依赖与冲突。保留其他已部署功能，不将工作目录中的未提交改动带入。
2. 在发布工作区完整构建；确认 Bridge 下载包及托管沙箱路径保持现状，实际域名仍指向 Dev Web。保存构建版本和原发布指针。
3. 发布前重新比较活动版本、服务配置和当前任务。短暂停止接单，在没有活动执行租约时备份 Dev 数据库并运行增量迁移 0113–0115；执行账号迁移预览和应用，核对原身份与历史数据归属。
4. 一次切换 Dev Web/Worker，保留 Bridge/托管 Runner 进程与设备别名。核对新版本健康、员工账号、管理员入口、组织/配发、文件与旧域名路径；检查既有功能和设备心跳。更新实际发布回执后才标记验收。
5. 失败时恢复上一版服务指针，保留备份和失败证据；数据库增量字段不通过自动删表回滚，账户密码不回退到共享员工默认值。迁移幂等，可在修复后重新运行。

隔离验证覆盖迁移预览零写入、原 ID 保留、重复执行、改密后保留、撤销与停用保持、用户名冲突整批回滚、管理员默认密码拒绝；登录 HTTP、页面/设备/回调/下载路径和深链接回归通过。
