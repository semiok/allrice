## 1. 结果与权限边界

内部检查只回答：同一固定候选的非正式分发产品、安全、兼容与真实设备观察是否完整。报告分别给出 `internalReady`、`internalBlockers` 和 `externalDistributionPending`。`internalReady: true` 不能解释为签名包可分发或正式发布完成；外部分发断言仍逐项登记待验，即使内部全部通过也不自动清空。

以下字段永远为 false：`releaseEligible`、`authorizationGranted`、`deploymentExecuted`、`migrationExecuted`、`flagsChanged`、`gaDeclared`。检查器不连接服务、调用模型、执行实验、启动 App、访问 Keychain、部署、迁移、修改开关或生成授权。缺失证据是阻断，不是提示后默认放行。哈希和字段一致只证明相对于可信 pin 的材料完整性，不能认证日志真实发生、操作者身份或 Apple 验证链；原始观察仍需人工核实。

内部开发包可采用已有 development / ad-hoc 构建路径，必须如实注明未公证、非正式分发，受信更新未配置时继续关闭。不得修改系统安全保护、删除 quarantine、放宽 Gatekeeper/entitlements、伪造发布者或给生产更新器注入测试信任根来获取“通过”。无法在现有安全边界内运行的用例继续阻断内部验收，不因账号缺失而改成 skipped 成功。

## 2. 清单与不可改写的 preparation

内部 manifest 精确字段如下，未知或缺失字段拒绝；这不是通过实例：

```text
schema = allrice-p27-internal-readiness/v1
acceptanceId / sourceSha / createdAt
preparation = {path, sha256, bytes}
evidence = [{caseId, file: {path, sha256, bytes}}]
blockers = [{id, reason, owner}]
```

`sourceSha` 必须是本次实际完整候选 SHA，`createdAt` 为真实封存时间。`preparation` 指向同一专用、脱敏、只读 evidence 根内原始 P28 `allrice-p28-release/v1` 准备清单字节，先核对其独立审查过的 SHA-256 与字节数，再**原样**交给原检查器的 `gate=prepare`。不得在内存或文件中删除字段、清空阻断、填假发布者、合成一份宽松 release manifest 再代为校验。

这一实际 preparation 自身必须满足：

- `evidence`、`blockers`、`unsupported` 均为空数组；`authorizations.dev / tenant / prod` 均为 null。它只承载候选准备材料，不夹带另一套验收、豁免或发布授权。内部未解决事项如实放在外层 `blockers`；固定的外部分发断言由本页映射保留在 `externalDistributionPending`，不能把产品安全缺口移进去。
- `signedClientRequired` 仍严格为 true；`clientPublisher` 保留原 `{teamId, bundleId, updateKeySha256}` 对象，未具备的值可为 null，不能用示例 Team ID 或测试密钥冒充正式身份。此时原 prepare 可成立，但其正式技术缺口不会变成通过。
- 七份真实 artifact 全部固定：`source`、`lockfile`、`dsh-upstream`、`web`、`worker`、`bridge-arm64`、`bridge-x64`；每项保留原 source SHA、version、build ID、独立路径、摘要和字节数。源码归档、真实构建来源和准确下载包均要留证，两个开发包必须同版本且来自同一候选。
- 原 lockfile / DSH pin、已发布迁移库存、新增迁移完整清单、所有执行开关默认关闭、`contractDeferred`、恢复模式与状态保全约束全部继续执行。没有证明安全兼容的旧包时保留 `forward-fix-only`，不得改为数据库降级、旧 credential reader、重新配对或清空 unknown。

仓库原 [P28 草稿](p28-release-manifest.draft.json) 没有真实候选，且保留历史 blockers / unsupported，不能直接作为本合同的有效 preparation。应根据实际候选另行编制、审查并固定完整材料；不要编辑原草稿使其看似通过，更不要自动擦掉已知阻断。内层与外层都以实际文件为准，草稿里的 null pin 有意导致拒绝。

## 3. 内部 receipt、实际方法与计费分支

每个内部 receipt 使用新的 schema，不接受原正式发布收据或把 parser 测试夹具改名充当证据。字段精确为：

```text
schema = allrice-p27-internal-evidence/v1
caseId / sourceSha / status=passed / execution=real-execution
observedAt / environment / tenantId / runId / command
artifacts / flagSnapshot / assertions / attachments / device
method / billing
```

共同字段沿用 P28 原始含义：`assertions` 是不重复、无额外项的 `{name, expected, observed}` 列表；只能从已经执行的真实观察归一化，不能把 expected 回显为 observed。`attachments` 至少一个，使用 `{path, sha256, bytes}` 绑定实际日志、页面、进程/退出码、账本或文件观察。客户端为 `environment=physical-macos` 和 `{id, architecture, osVersion, physical:true}`；其他场景沿用 `isolated` 或最终 Dev smoke 的 `dev`，且 `device=null`。

默认且除以下例外外唯一允许的 `method` 为 `real-end-to-end`。只有两架构的 `authenticated-update-metadata` 与 `invalid-signature-and-package-rejection` 可使用 `physical-component`，也可用真实端到端方法。组件观察必须在对应真实原生设备上运行实际安全实现，证明重放/降级、无效发布者/损坏包拒绝及无安装副作用；这不是 mock Apple 成功端口、单元测试夹具、跨架构静态检查或伪造 PID。组件方法不授予正式发布者认证，也不能用于 GUI、Keychain、排空、中断恢复或回退场景。

两个 `developer-id-signature-notarization` 场景没有内部断言，不提交内部成功 receipt；其他 45 场景均必须有 receipt。不能用“待 MET-143”替代实际开发包的 GUI 安装/配对/目录选择、真实 Keychain 保存读取与拒绝、重开、撤权、本地命令/Changeset/进程树取消、活跃任务排空、开发包中断恢复和兼容状态恢复。若相关产品路径尚无法安全演练，就登记内部 blocker 并继续实现，不能放宽方法或记录未执行成功。

`billing` 字段始终存在。除 `assistants-real-dsh-two-children-no-bridge` 外严格为 null；该场景复用 P28 v2 的两条明确分支：

- 当前用户验收只用 Codex 订阅：`{mode:"subscription", proof:{path,sha256,bytes}}`，在共通断言上增加 `immutable-subscription-route-proof-verified`、`whole-tree-actual-tokens-and-admissions-settled`、`subscription-result-route-ledger-na-digest-match`、`subscription-no-api-price-or-cost-receipts`、`subscription-unknown-token-follow-up-denied` 五项。proof 沿用 `allrice-p27-subscription-accounting/v1` 严格原始 snapshot / route / ledger / result / tree / admissions 关系；真实 Token 完整、NULL/N/A 非零现金、无 API 价格/费用回执、未知 Token 不释放。proof 与当前候选、Run、租户、原始附件绑定。
- 保留解析兼容性：`{mode:"token_metered"}` 加 `frozen-price-and-whole-tree-cost-receipts` 一项；不允许订阅 proof 混入。这只保留已有合同，不授权或要求当前验收调用任何 API 计费模型。

订阅不是免费 API，不可伪造单价/费用回执，不可把 NULL/N/A 改成 0，不可跳过实际 Token、整树准入、未结 hold 或后续 Worker 配额检查。当前 checker 自测不得调用任何模型或真实服务；后续真实 Codex 订阅执行由 MET-138/142 在明确范围内另行完成。

## 5. 证据约束与不能晋升的结果

- 内部 manifest、原 preparation、receipt 和附件均用实际文件 pin；路径必须相对同一专用 evidence 根，拒绝隐藏路径、路径越界、符号链接、特殊文件、缺文件、摘要/字节不符、重复 JSON key、未知 schema、重复/遗漏 case 与断言。不得使用用户主目录、源码根或凭据目录作 evidence 根。
- 原 7 天时效规则保留：未来、格式错误和超期时间拒绝，超期重验并重新封存，不能改历史观察日期。候选或包字节变化必须重新固定受影响材料，不能借旧构建收据给新包签字。
- 联合场景绑定全部七份 artifact，客户端绑定 source 与对应架构 ZIP；`compatible-redeploy` 的恢复证据仍额外绑定全部 `rollback/<id>` 目标摘要。只核对 sourceRoot 的库存不证明 checkout 干净，来源场景仍须实查 Git 与构建链。
- ARM / Intel 必须是两台不同、真实、原生架构设备，同一架构所有 receipt 的设备 ID 稳定一致，记录实际 OS 版本；单机、Rosetta、交叉构建、静态签名检查或设备名改写均不等价。客户端每个非签名产品场景仍独立验收。
- `flagSnapshot` 保留原 14 个准确开关名和真实布尔观察。内部开发/隔离场景的启用需另有明确授权；最终 Dev smoke 仍须真实默认关闭。清单不改变开关，未获授权不能为凑材料部署或开启真实租户能力。
- 元数据/包拒绝、隔离、撤权、精确审批、unknown 不重放、Token/预算、用户更改保护、Keychain、进程树停止、迁移/状态保全的失败均是内部 blocker。不能放入外部分发待办、删断言或用 `unsupported` 豁免。旧失败与未知风险保留，修复后在固定候选重验。

正式发布检查器不接受内部 schema 或内部 receipt。未来取得 MET-143 条件后，应重新固定正式签名产物及准备/发布清单，使用原正式 receipt schema；不能只把内部 JSON 改名、添两个签名布尔值或把 `internalReady` 写入 RC。尤其签名包重装、实际 Keychain 身份/ACL、升级排空、中断恢复、回退和原生 GUI 必须按最终双架构包重新验证；内部开发包观察不能证明这些正式包行为。

## 6. 调用与执行顺序

所有参数显式提供，不读取环境变量中的隐式授权；没有 `--gate` 或 `--allow-unsigned` 开关。占位值必须替换为实际审查过的路径与可信 pin：

```bash
node scripts/acceptance/platform/p27-internal-readiness.mjs \
  --manifest /absolute/redacted-evidence/internal.json \
  --evidence-root /absolute/redacted-evidence \
  --source-root /absolute/pinned-candidate-checkout \
  --source-sha FULL_ACTUAL_CANDIDATE_SHA \
  --manifest-sha256 INDEPENDENTLY_REVIEWED_INTERNAL_MANIFEST_SHA256
```

退出码 0 只表示内部材料条件成立，2 表示拒绝；请同时阅读 `internalBlockers` 与始终独立保留的 `externalDistributionPending`。退出 0 不授予环境操作权限，也不把原 `dev / rc / tenant / prod` 变绿。草稿 `sourceSha/preparation` pin 为 null、evidence 为空，必须拒绝；检查器自测使用合成材料仅验证拒绝边界，不构成产品成功观察。

执行顺序是 MET-148 独立 PR 审查和自测 → MET-138 / MET-142 完成真实网页审批 → Bridge 执行 → 结果返回/刷新恢复闭环及上述内部矩阵 → MET-147 集中 UX 收口。MET-143 的账号/正式身份/公证与分发准备可并行，不作为前述产品研发的前置依赖，但始终是正式分发验收的前置。MET-148 本身不执行后续真实模型/服务联验、不部署、不改工单状态；真实缺设备、权限或产品实现的事项继续登记并解决。

## 7. MET-142：显式、保守的历史观察复用

默认 `{caseId,file}` 仍严格要求同候选、同产物的 v1 receipt，不会自动推断复用。只有显式 `{caseId,file,reuse:true}` 才把 `file` 解释为以下独立 wrapper；`reuse:false`、未知字段和旧收据直接换 source SHA 均拒绝。当前 target preparation 仍完整经过原 prepare gate。正式 P28 checker 不接受此 wrapper，未增加正式分发豁免。

```text
schema = allrice-p27-internal-evidence-reuse/v1
caseId
originalReceipt = {path,sha256,bytes}
testedSourceSha
testedArtifacts = {每个所需 artifact ID: {path,sha256,bytes}}
targetSourceSha
targetArtifacts = {每个所需 artifact ID: sha256}
impactReview = {path,sha256,bytes}
```

`originalReceipt` 必须是原始不可改写的 `allrice-p27-internal-evidence/v1`，不能指向另一个 reuse wrapper。其真实方法、run/device、原 `observedAt`、原 source/artifact、附件和计费原证明全部按同一收据校验逻辑检查；仅 artifact/source 绑定使用明确的 tested pins。客户端只要求原 receipt 对应的 source 与本架构产物，不虚构一份包含无关七件产物的旧 preparation。需要 rollback 目标的场景继续要求完整额外 pins。所有 tested 实体文件实际读核摘要/字节，target pins 必须与当前 preparation 一致。

审查文件字段精确为：

```text
schema = allrice-p27-internal-impact-review/v1
caseId / originalReceiptSha256 / testedSourceSha / targetSourceSha
reviewedAt / reviewer
codeBoundary = {path,sha256,bytes}
assertions = [{name,impact:"unaffected",rationale,boundarySha256}]
```

逐断言 review 必须覆盖原收据全部断言、无遗漏/重复，绑定同一 codeBoundary；`affected`、`unknown` 或空理由拒绝。审查时间必须不早于观察且自身有效；**原观察继续受原 7 天规则约束，review 不续期，也不产生新的实测时间**。

`codeBoundary` 是 `allrice-p27-code-boundary/v1` JSON，包含 `testedSourceSha/targetSourceSha/policy/testedTreeSha256/targetTreeSha256/patch`。policy 固定为 `unchanged-product-tree-and-artifact-bytes/v1`。检查器从 `sourceRoot` 的本地 Git 对象重新读取两个完整 commit、全部 tree 条目的 path/mode/type/blob，并用禁用外部 diff/textconv 的 bounded Git 命令重新计算完整 binary/full-index/no-renames patch；文件与真实计算不一致即拒绝。只能排除代码中 `REUSE_NON_PRODUCT_PATHS` 明列的验收合同/checker 文档文件，不能由 reviewer 自选路径或用一个 `affected:false` 替代。允许路径也必须是普通非执行 blob，不能换成符号链接。其余产品树必须完全相同；除 source 归档外所有所需 artifact 必须保持原字节。

这是 **gate/docs-only 候选变化** 的保守复用，不是逐组件无影响分析。应用、依赖、构建配置、权限模式或非源码包字节变化一律不复用，即使作者声明“行为相同”。它不使 B5 GUI/Keychain、已超期观察或更早 Worker/provider/accounting 代码上的历史记录自动通过。`source-build-package-provenance` 和 `dev-final-sha-login-history-downloads-flags-smoke` 固定要求新的目标候选证据。

报告将通过校验的 `freshEvidence` 与 `reusedEvidence` 分列；后者保留 tested/target pins、原 observedAt、reviewedAt，并始终 `executedOnTarget:false`。两类共同接受物理设备身份和跨架构约束，失败条目不会计入有效复用。哈希与 Git 等同性只证明相对于可信 pins 的材料与边界一致，不能认证原日志、操作者身份、源码归档建造链或实际执行；源码/构建来源仍必须另有 fresh 原观察。账本结构证明不能替代 E2E/physical 方法，不生成任何 receipt 或 observed=true。历史非 v1 原件如需忠实归一化，必须另行人工保留、审查原始附件、source 与时间；本实现不自动转换。所有发布/部署授权字段继续为 false。
