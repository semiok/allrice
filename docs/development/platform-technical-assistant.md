## Platform repository credential — MET167 PR4a1

The technical assistant has a separate repository authorization panel. Each active platform administrator registers a fine-grained GitHub token for the fixed repository `semiok/allrice` (numeric ID `1323769790`). Grant Contents and Pull requests read/write, and Actions, Checks and Administration (branch protection) read. This slice stores configuration only; it does not yet create a PR, check remote permissions or claim that CI passed. GitHub's [reference](https://docs.github.com/en/rest/git/refs#create-a-reference), [pull request](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request) and [workflow run](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run) endpoints document the corresponding permissions.

An employee's MCP OAuth connection and the platform's OAuth client secret remain separate. Product code does not import the operator's Composio or local Git credentials. Tokens stay server-side, encrypted with the existing `ALLRICE_MCP_CREDENTIAL_KEY`; authenticated additional data binds the administrator, private scope, fixed repository and credential revision. The current administrator's actual login is rechecked for every read and mutation. Rotation/removal uses revision CAS and records an audit event without the secret. A retained removal revision prevents an old operation from becoming valid again.

`GET/PUT /api/v1/admin/technical-assistant/repository-credential` require current platform authority; writes also require same-origin JSON and a bounded body. Public responses contain only configuration facts. A configured credential is not a remote readiness or publication receipt. An unknown write is reconciled through its saved request ID, never automatically replayed. Ordinary accounts and other administrators cannot read the private credential. Removing a token remains possible if the encryption key is unavailable.

The management console has a technical assistant under Platform settings. It reads existing Web/Worker readiness, release SHA, trusted Worker resource samples, durable queue/resource waiting, database lock waiting, Run/operation states and employee feedback references. Each collection carries its source, environment, time window and freshness. A failed collection is unknown; no missing counter is displayed as measured zero. Run, operation and feedback lists are limited to the most recent 20 records in 24 hours. A full ID can refer to an older record.

The Web readiness target uses its configured `WEB_PORT` or `ALLRICE_TECHNICAL_WEB_HEALTH_URL`. A Worker running diagnostic tasks must receive that explicit URL at the actual co-located Web port, ending in `/api/health/ready`. The Worker readiness target must be configured as `ALLRICE_TECHNICAL_WORKER_HEALTH_URL` at the actual co-located Worker port, ending in `/health/ready`. Both are trusted deployment configuration, not browser-supplied URLs. Invalid, absent or failed probes preserve unknown state. These probes do not support a remote Worker deployment yet. `/health/ready` includes `x-allrice-release-sha` when the configured release SHA is valid.

Platform authority is the active database user plus the server-owned platform allowlist. The dedicated admin portal authenticates existing sessions against the hidden `allrice-platform/control-plane` scope. It does not require or create company membership, and it does not use company selector headers. Ordinary employee and company-admin identities cannot use these endpoints. An admin session is rejected on the employee portal. Hidden scope initialization continues to use the existing trusted bootstrap mechanism.

A problem stores structured source references, its environment, status/category/severity, evidence count and immutable status events. Repeating a capture returns the canonical stored problem without incrementing its count. Each different source counts once. An administrator can group a new source under an existing problem explicitly; no model guesses causality. An already linked source retains its canonical problem. Updates use an expected version; a conflict returns the actual latest record. An ambiguous browser write must be read back before retrying.

The collector and problem records exclude conversation bodies, scripts, SQL text, credential values and raw provider errors. Existing business records remain authoritative and are not rewritten by diagnostics. Problem data lives in separate platform tables. Refreshing diagnostics does not create a problem or invoke a model.

Routes:

- `GET /api/v1/admin/technical-assistant`: bounded current facts and latest 100 problems.
- `POST /api/v1/admin/technical-assistant`: `{kind, id, issueId?}` for an existing Run, operation or feedback reference.
- `GET /api/v1/admin/technical-assistant/issues/:id`: stored problem with its latest 100 evidence references.
- `PATCH /api/v1/admin/technical-assistant/issues/:id`: `{ifVersion, status, category, severity}`.
- `GET /api/v1/admin/technical-assistant/tasks`: the current administrator's latest 20 diagnostic tasks.
- `POST /api/v1/admin/technical-assistant/tasks`: `{requestId, question, issueId?}` creates or returns the same diagnostic task.
- `GET /api/v1/admin/technical-assistant/tasks/:id`: owned task, answer, measured usage and at most four durable diagnostic receipts.
- `DELETE /api/v1/admin/technical-assistant/tasks/:id`: stops the owned task through existing Run cancellation.

All routes require platform authority. Writes additionally require a same-origin browser request. Responses are private/no-store. Admin-only wire schemas are exposed through the pure browser-safe `@allrice/database/technical-contracts` subpath; they do not change the Bridge contracts or require a new native package.

PR1a establishes deterministic diagnosis and problem persistence. PR1b runs a bounded model diagnosis through the existing Run/Job queue, Worker runner and DSH adapter. The private composition exposes exactly one native tool, `platform.technical.diagnostics`, with strict `{scope: "current"}` input. It reuses the same bounded collector and optionally reads the linked problem. No URL, SQL, command, company identity or other target can be passed by the model. The tool is absent from ordinary employee manifests; its Broker route requires the original authorized Worker lease and hidden platform task context.

Task creation freezes the platform model settings/revision, system prompt/digest, workflow version, source release and deadline in the enqueue transaction. A request ID is scoped to its real administrator; an unchanged retry returns the original task, while a changed input conflicts. The hidden per-admin execution workspace uses the existing platform test provisioning mechanism and does not add company membership or employee sessions. Tasks are owner-private, even between platform administrators.

There is one queue attempt, no automatic model retry, a maximum five-minute deadline, eight logical model requests and four diagnostic receipts. Existing DSH provider retries remain governed by the pinned adapter. Cancellation, timeout, current platform authority and the Worker lease are checked before execution, on heartbeat, on model progress, at the Broker and before completion. A successful diagnosis must contain a persisted receipt from its current attempt. Receipts are ordinary durable Run tool events with input/output digests; this read-only task does not create a new runtime-operation target or a second executor.

Measured token usage is recorded for successful tasks. A failed, canceled or timed-out task can retain the known usage lower bound from its original Worker/attempt, without changing its terminal status or answer. Repeated cumulative observations are not added twice; a foreign lease cannot settle usage. Missing usage and actual currency cost remain unknown. Logical request counters are execution limits, not billing receipts. The page can explicitly refresh terminal task details to recover late usage facts. An uncertain browser submission is read back before retrying the same request ID.

PR1 does not implement scheduled quality checks, repair agents, GitHub publishing, deployment control or autonomous recovery.

Verification uses the existing PostgreSQL fixture and Vitest. The technical facts suite covers normal/queued/absent/stale/failed-source facts, failure/feedback references, content exclusion, concurrent canonical capture/grouping, version conflicts and revoked authority. The task suite tests transactional concurrent deduplication, frozen revisions, owner/employee isolation, exact private DSH schema with the pinned native runtime and real Broker/DB, admission denial before a model request, receipts, lease fencing and terminal usage settlement. Worker lifecycle cases cover success, failure, cancellation and both deadline paths with a controlled model substitute. The existing unified-login HTTP suite additionally covers an administrator with zero memberships through password login, signed portal session and the technical API. Dev acceptance must exercise actual page clicks and one real native diagnostic task, its persisted details and receipts, terminal refresh, and denied ordinary-account access.

## Private daily fixed checks — MET167 PR2b

The existing Automation tick can run the existing `project.static.v1` corrected fixture once daily in Asia/Shanghai. Each real platform administrator has at most one undeleted private rule. It defaults to absent/off; the administrator explicitly enables it. Normal employee Automation list, read, update, delete and run-now endpoints exclude this reserved binding.

`GET /api/v1/admin/technical-assistant/quality/schedule` reads the owned current rule and latest 20 owned occurrences, including deleted-rule history. `PUT` accepts strict `{expectedRevision, enabled, time}`; `DELETE` accepts `{expectedRevision}`. Configuration requires the actual current administrator login and same-origin write, and uses optimistic revision checks plus the existing audit table. An unknown write is read back before another action.

A due rule freezes its revision, owner, private scope, scenario, scheduled time, configuration digest and a fifteen-minute dispatch deadline. The existing rule lock and partial occurrence index deduplicate concurrent ticks. Its occurrence UUID derives the stable quality request identity. QA, Employee Run, Job and the occurrence association commit in the original enqueue transaction. Bounded recovery scans unbound queued occurrences; a lost acknowledgement is reconciled by reading the committed association first. Transient preparation errors remain recoverable until the frozen deadline. Definitive authority/configuration failures are recorded as not executed, never passed.

The next due time advances directly into the future. Expired days and days overlapping an unfinished check do not create catch-up tasks. Pausing, changing or deleting a rule ends only its unbound old occurrences; an already admitted Run keeps its original frozen input and uses existing cancellation and physical cleanup. Current account, allowlist, platform membership, reserved assignment, employee publication and Worker lease guards still apply during execution. Reports are accepted only with the original canonical successful Job and complete passed evidence.

Scheduled checks are static only. Their internal correlation ID is not a browser login and is not inserted into the login table. Scheduled live checks are rejected; no login is borrowed or fabricated. This slice proves the existing fixed static fixture through daily dispatch, persisted report, actual admin details and exact source/page/PNG downloads. Arbitrary projects, repair agents, publishing and the remaining MET164/166 capability/performance matrix retain their separate scope.

The CLI verifies the fixed origin, clean checkout, latest remote main, every blob, file mode, root lockfile and dependency configuration. It includes no Git credentials, local files or secret environment files. A missing or outdated catalog disables new tasks rather than substituting another repository or source version.

The administrator creates an owner-private repair task using the existing published Rice employee, Employee Run, Job, Worker, DSH, cloud operation ledger and immutable delivery mechanisms. The real administrator login, current allowlist, private deployment, original Worker lease, deadline and candidate are checked at dispatch, execution and publication. A stable request ID supports readback before retrying an uncertain write. The same completed physical result can resume publication without executing the candidate again.

Only `packages/project-runtime/src/command-output.ts` is editable, and only its last masking regexp and literal replacement may change. Trusted code remains byte-identical. The private native `platform.repository.repair` tool supports read, bounded apply and verify; it accepts no repository path, command, URL, alternate test or authority override. There are at most three candidate revisions, one queue attempt and a thirty-minute task deadline. An actual original failure and a subsequent pass of the same eight trusted assertions are required; text claiming success is insufficient.

The existing pinned runsc backend restores every archived file, checks material hashes and runs the fixed harness without network, host mounts or monorepo dependency installation. `GET /api/v1/admin/technical-assistant/repair/baselines` returns current registered baselines. `GET`/`POST /api/v1/admin/technical-assistant/repair` list or create owned tasks; `GET`/`DELETE .../repair/:id` read or cancel a task. `GET .../repair/:id/artifacts/:artifactId` downloads the exact immutable candidate or verification report after owner and byte-checksum validation. All routes require platform authority, and writes require same origin. Other administrators and ordinary employees cannot access a task or its files.

The detail page reports the original failure, current candidate, actual assertions, execution identity, cleanup and download versions. A task is accepted only when its canonical Job succeeded with persisted physical evidence. This slice does not run full pnpm checks, install monorepo dependencies, merge a GitHub PR or publish a candidate. Those capabilities and the remaining MET164/166 matrices require their own evidence.

  --repository-dir=/absolute/clean/release \

  --dependency-cache=/absolute/operator-owned/cache \

The compiled verifier has a fixed 768 MiB memory limit and a fixed 384 MiB heap only for the UID 1002 compiler. It consumes two of the existing 640 MiB capacity units. An old or mismatched live watchdog cannot advertise compiler support merely because a new file was copied to the VM. The separate UID 1002 compiler performs an offline, frozen install with lifecycle scripts and pnpmfile disabled, followed by the two packages' original `tsc -p tsconfig.build.json` scripts. Original source/configuration and derived installation files have separate manifests. UID 1001 then executes the same eight original assertions through the actual package export `@allrice/project-runtime`, resolving to `dist/index.js`. Neither child can rewrite the parent's assertions or attestation. The parent rechecks source and generated bytes after child execution. `workBytesAfterBuild` measures logical bytes at the post-build snapshot; it is not a peak memory or peak disk measurement.

The detail page displays actual dependency/build exits, compiler versions, the frozen timeout/memory limits, package output hashes and the production entry point. A before-build failure is a harness failure and does not invoke a repair model. A completed original assertion failure and passed repaired assertions have separate recorded observations. ## Exact completed review consumption and main merge — MET167 PR5a

A new canonical fixed merge Run consumes the persisted complete independent review without reopening its old execution lease, deadline, login, credential or deployed employee version. Its proof binds the original frozen input, canonical Job/Run and native root/child identities, the actual adopted report and original/effective report digests, the three immutable artifact byte digests, source author chain and pre/postflight remote receipts. Explicit cancellation, revocation, missing/replaced artifacts and a same-content revise verdict still reject consumption. The original live review completion guard remains unchanged. Verdict registration and consumption share a content transaction lock; the historical native root is locked before current authority, and the new lease is rechecked after lock waits.

The browser supplies only the saved publication/review identity, expected subject digest, request ID and credential revision. The trusted Worker fetches the fixed repository, exact current head/base, all four original current CI receipts and the strict main protection policy. It can mark this exact draft ready and request a merge commit with the exact head SHA. Because GitHub's [merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) compares head only, the executor requires strict up-to-date checks from GitHub Actions for all four original jobs, including administrator enforcement, and rejects force-push/deletion permissions. It never installs branch rules, bypasses protection, force-updates main, or changes the merge method. A missing or unreadable protection policy blocks writing. See GitHub's [protected-branch semantics](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

A failed action with no external START may consume a new completed review in a new immutable merge generation for the same publication. Admission serializes all generations; previous requests retain their own evidence and readback. Any ready or merge START fixes that generation and forbids changing its proof. Each external write has a durable immutable intent before dispatch, one queue attempt and a five-minute deadline. An unknown merge acknowledgement preserves that intent. A fresh currently authorized reconciliation Run issues only reads, checks the actual merge commit's exact base/head parents and tree, and verifies that main contains it; it never emits another merge write. Current user/login/credential and actual private membership/workspace/organization rows stay fenced until the final local request gate completes. After lock waits the gate checks the current login expiry again using the database clock and bounds the request by login expiry as well as the lease. Cancellation or revocation after that boundary cannot recall an already sent remote request, so an unconfirmed result remains unknown until readback. No database transaction waits on GitHub network I/O.

Private/no-store admin routes are `GET/POST /api/v1/admin/technical-assistant/repository-merges` and `GET/DELETE /repository-merges/:id`. Normal employees and other administrators cannot operate on the records. Unknown browser submissions retain their exact request across reload, first read back that request, and may explicitly retry only its unchanged ID and payload. The details distinguish an actual main merge receipt from Dev publication; PR5a does not deploy or claim Dev acceptance.

Deterministic verification uses isolated PostgreSQL, the production native assistant protocol and storage, strict HTTP handlers and Chromium with synthetic GitHub/CI responses. This proves request deduplication, protected-base refusal, exact merge parent/tree validation, cancelled/revoked/missing/adoption fences, old authority expiry with fresh authority, lease expiry after lock waits, concurrent same-content revise registration, and unknown-response read-only reconciliation. It does not substitute for an actual product candidate, real model review or real GitHub merge. Product acceptance requires a current configured repository token and a strictly protected main; neither operator credentials nor the feature PR's green CI fill those gaps. Bridge inputs, Office/PDF and ordinary programming/preview contracts are unchanged.
