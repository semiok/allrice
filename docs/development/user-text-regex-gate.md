# 门禁：不新增“用正则判断用户原话”的代码

MET-210 #2，规则见 MET-220 R1。2026-10-26 加入，是 MET-210 三道“只减不增”门禁的第一道。

## 拦什么

R1：理解用户交给模型；授权靠来源（真人消息）和确认卡；正则只用来放行明确的格式，不能用来拒绝用户。对用户原话做正则匹配、匹配不上就拒绝、报错或不执行，是要逐步去掉的做法（MET-210 #2），新代码不能再加。

“输入是不是用户原话、匹配不上会不会拒绝”没法静态判断，所以门禁宁多勿少：`apps/`、`packages/` 产品代码里（不含测试、夹具、构建产物和 `apps/web/app/chatflow/dsh-upstream/` 这份 DSH 源码拷贝），凡是拿中文措辞做匹配的地方都算一处：

- 含汉字的正则字面量（转义也解开）；`[\u4e00-\u9fa5]` 这类字符范围、`\p{Script=Han}` 表示“任何汉字”，不算措辞，不报；
- `RegExp(...)` / `new RegExp(...)`，模式能在同一文件里算出来（常量、模板、`+`、`.join()`、`.map()`、`.source`）且含汉字；
- `includes`、`startsWith`、`endsWith`、`indexOf`、`lastIndexOf`、`match`、`matchAll`、`search` 的参数是中文；在中文关键词表上逐项匹配（`WORDS.some((w) => text.includes(w))`）；判断是否在中文词表里（`WORDS.includes(text)`、`new Set(WORDS).has(text)`）。

现存的 191 处（36 个文件）写在基线 `scripts/user-text-regex-gate.baseline.ts` 里，每组写明文件、所在函数、分类和用途。CI 只拦基线之外新出现的。

## 怎么跑

```bash
pnpm user-text-regex:verify
```

约 3 秒，不需要数据库。默认和 `origin/main` 的合并基准比较基线；`--base <提交>` 指定基准，`--list` 列出每一处的当前行号和状态（基线里的分类、例外类别，或 `NEW`），`--json` 输出全部结果。`pnpm test` 也会跑 `scripts/user-text-regex-gate.test.ts`。

CI 在 `validate` 任务的 `pnpm typecheck` 之后跑这一步，`--base` 是 PR 的基准提交（推到 main 时是推之前的 main）。

## 被拦下怎么办

1. **先改做法**：理解交给模型，模型给结构化参数，服务端校验结构；需要用户点头的走确认卡；真人来源校验（`assertEmployeeChatHumanSource`）保留。做法见 MET-210 #2 和 #576（周期提醒）。
2. **确实不是 R1 的**，在这一处正上方写例外，理由写在同一行、至少 10 个字，说清楚“没匹配上为什么不会拒绝用户”：

   ```ts
   // r1-exempt(format): 只认“第 N 页”这一种写法，不命中照常交给模型
   const page = /第(\d+)页/u;
   ```

   同一行里有几处时，可以紧挨着写成行内注释：`[/* r1-exempt(own-text): … */ /资料依据/u, …]`。类别只有四种：

   | 类别            | 什么时候用                                                                                   |
   | --------------- | -------------------------------------------------------------------------------------------- |
   | `format`        | 只认一种明确写法：命中就放行或取值，不命中照常交给模型或走默认流程，不拒绝、不报错、不跳过   |
   | `own-text`      | 匹配的是系统自己写出的固定文本或标记（含提问卡上系统给的选项），不是用户原话，也不是模型输出 |
   | `external-text` | 匹配的是外部系统写出的固定文案（网页拦截页、第三方报错）；外部给了错误码就用错误码           |
   | `display`       | 只影响展示（高亮、截断、排版），不影响做不做、怎么做                                         |

   一条例外只管一处：写在语句、属性或类成员上方，或紧挨在这一处前面。写在行尾、写在外层函数上、一条管两处、类别不认识、理由太短、下面没有匹配的例外，门禁都会报错。例外在 PR diff 里可见，复核时按 R1 审。

3. **不要把新代码加进基线。** 基线只减不增：CI 会拿 PR 的基线和基准提交的基线比较，多出来的条目直接失败。条目可以跟着代码换文件、换函数（按匹配文本计数）；在同一个函数里原地改一条正则，算替换原来那条，不算新增，但每个函数的条数不能变多。原地改会在基线的 diff 里露出来，复核按 R1 审：能迁就迁，不要靠多加几个说法来修“说法没匹配上”的问题。

## 基线怎么减

- #2 迁移一处后，删掉代码里的匹配，也删掉基线里对应的那一行；门禁会报“基线里有、代码里已经没有”的条目，提醒你删。
- 分类 `reject`、`decide`、`extract` 是 #2 要迁的（10-26 共 146 处）；`format`、`own-text`、`external-text`、`display` 是核对过不算 R1、只因为第一个 PR 不改产品代码才放在基线里的，以后改到那个文件时可以顺手换成代码里的例外注释。
- 基线里周期提醒（`recurring-task-intent.ts`）记为 `format`：#576 之后，命中句式只是免确认的快速通道，没命中出确认卡，不再拒绝。

## 不覆盖的

- 相等比较（`text === '确认'`）；
- 在别的文件里拼出来的正则或关键词表（只在同一文件里追常量）；
- 纯英文措辞的匹配；
- Swift、Python 等非 JavaScript/TypeScript 源码。

改门禁本身（扫描范围、跳过的目录、例外类别）同样走 PR 复核。
