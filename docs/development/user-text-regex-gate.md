# 门禁：不新增“用正则判断用户原话”的代码

MET-210 #2，规则见 MET-220 R1 和仓库 `AGENTS.md` 第 0 节。2026-10-26 加入，是 MET-210 三道“只减不增”门禁的第一道；2026-11-03 按 MET-240 更新意图和授权边界。

## 拦什么

R1：产品代码不得用正则、关键词或词表判断用户话语的意图、意愿或授权。理解交给模型，把关靠真人消息来源、权限、工具参数校验、DSH 原生提问和审批、可见回执。即使命中后只是放行、未命中照常交模型或出确认卡，也不能用匹配结果认定用户想做或已同意某事、免确认或决定授权。

不判断意图或授权的技术用途可保留，例如时间等格式解析、系统自己的错误码匹配、报错脱敏；格式解析不能成为授权或免确认的依据。

现有静态门禁不能完整判断输入来源、调用链或意图／授权语义，所以宁多勿少；通过门禁不等于符合上述规则，仍须独立复核用途。以下是扫描器现有检测范围，本次只更新文档，不改实现、基线或例外类别。范围是 `apps/`、`packages/` 的产品代码（不含测试、夹具和构建产物）。“措辞”指中文，或者至少两个英文请求用词、其中一个是虚词（`please do`、`please install`、`don't remember`）；大小写不论，`STOP_NOT_CONFIRMED` 这类带下划线或数字的代码不算（见脚本里的 `englishWording`）。下面这些都算一处：

- 含措辞的正则字面量（转义也解开）；`[\u4e00-\u9fa5]` 这类字符范围、`\p{Script=Han}` 表示“任何汉字”，不算措辞；
- `RegExp(...)` / `new RegExp(...)`，模式算出来含措辞；
- 按名字使用一个含措辞的正则（`test`、`exec`、`match`、`replace`、`search`、`split` 等，包括 `new RegExp(PATTERN)` 复制出来的）：每次使用算一处，写正则的那一行不再单独算。所以给现有的正则加一个新调用方是新的一处，把正则提成常量前后都只算一处；
- `includes`、`startsWith`、`endsWith`、`indexOf`、`lastIndexOf`、`match`、`matchAll`、`search` 的参数是措辞；在措辞词表或词典里判断成员、按键查找（`WORDS.includes(text)`、`new Set(WORDS).has(text)`、`TABLE[text]`、`text in TABLE`、`new Map(...).get(text)`）；和措辞做相等比较或 `case`。

名字按作用域解析：同一文件里的常量、相对路径 `import` 进来的常量（具名、`import * as`、经 `export … from` 转出的都算）、迭代出来的元素（`for...of`、`some`/`find`/`map` 等回调的参数、解构、`Object.keys/values/entries`、`Map`/`Set` 的 `keys/values/entries`、规则表里的字段）、对象属性和类的静态属性，以及 `?:`、`??`、`||` 的两边。

2026-10-26 首版登记的 264 处（56 个文件）写在基线 `scripts/user-text-regex-gate.baseline.ts` 里，按“文件 + 所在函数 + 匹配文本”登记，每组写明历史分类和用途。CI 拦截静态识别的基线外新增，并校验基线只减不增及例外注释；基线或例外的存在不代表语义合规。

## 怎么跑

```bash
pnpm user-text-regex:verify
```

约 4 秒，不需要数据库。默认和 `origin/main` 的合并基准比较基线；`--base <提交>` 指定基准，`--list` 列出每一处的当前行号和状态（基线里的分类、例外类别，或 `NEW`），`--json` 输出全部结果。参数写错时退出码是 2。`pnpm test` 也会跑 `scripts/user-text-regex-gate.test.ts`。

CI 在 `validate` 任务的 `pnpm typecheck` 之后跑这一步，`--base` 是 PR 的基准提交（推到 main 时是推之前的 main）。

## 被拦下怎么办

1. **先改做法**：理解交给模型，模型给结构化参数，服务端校验结构和权限；需要用户点头的走 DSH 原生提问和审批，以结构化结果和可见回执为准；真人来源校验（`assertEmployeeChatHumanSource`）保留。做法见 MET-210 #2；#576 的历史快速通道不能作为免确认依据，见下文。
2. **确属不判断意图或授权的技术用途**，在这一处正上方单独一行写例外，理由写在同一行、至少 10 个字，说明为什么不判断意图或授权、不免确认，且没匹配上不会拒绝用户：

   ```ts
   // r1-exempt(format): 只提取页码，不判断意图或授权，不命中照常交给模型
   const page = /第(\d+)页/u;
   ```

   例外写在包含这一处的语句、属性、类成员或 `case` 的上方；同一行有几处，或者这一处在 `else if (...)` 条件里，就紧挨着写成行内注释：`/* r1-exempt(format): … */ /^第\d+页$/u.test(text)`。类别只有四种：

   | 类别            | 什么时候用                                                                                   |
   | --------------- | -------------------------------------------------------------------------------------------- |
   | `format`        | 只提取明确技术格式的值，不判断意图或授权、不免确认；未命中照常交给模型或默认流程，不拒绝、不报错、不跳过 |
   | `own-text`      | 匹配系统自己写出的固定文本或标记，不是用户原话，也不是模型输出；不得靠匹配回传的选项文案认定授权 |
   | `external-text` | 匹配的是外部系统写出的固定文案（网页拦截页、第三方报错）；外部给了错误码就用错误码           |
   | `display`       | 只影响展示（高亮、截断、排版），不影响做不做、怎么做                                         |

   一条例外只管一处。写在行尾、写在带花括号的外层函数上、一条管两处、类别不认识、理由太短、下面没有匹配、写在门禁读不到的地方（JSX 里、字符串里、`}` 前面），门禁都会报错。正则被按名字使用时，例外要写在每次使用的地方，写在正则定义上会报错。箭头函数只有一个表达式时（`const f = (t) => /…/.test(t)`），写在这个常量上方就算这一处的例外。

   新加的有效例外注释不会让 CI 失败，但会列在输出的 “Review under MET-220 R1” 里，在 GitHub 上作为警告标在 PR 对应的行上。静态检查接受注释不等于认可用途；四种类别都不能用于用户意图／授权判断或免确认，复核时按当前 R1 审。

3. **不要把新代码加进基线。** 基线只减不增：CI 拿 PR 的基线和基准提交的基线做匹配，找不到对应的就失败。能对应上的只有三种：
   - 文件、所在函数、文本都一样；
   - 分类相同、文本相同，文件或所在函数有一个没变（跟着代码搬家）；
   - 分类相同，文件和所在函数都没变（原地改了这条正则）。

   所以每个函数的条数、按现有分类计算的 #2 待迁条数都不会变多，历史非 #2 分类的条目也不能拿来换一条新的 #2 条目；同一条从非 #2 改成 #2 分类，也算新增。搬家、原地修改、把分类从 #2 改成非 #2，都会列进 “Review under MET-220 R1”，并在基线文件上标警告；这些分类和警告不代替当前语义审查。原地修改要按 R1 审：能迁就迁，不要靠多加几个说法来修“说法没匹配上”的问题。又搬家又改名又改文本的，拆成两个 PR。

## 基线怎么减

- #2 迁移一处后，删掉代码里的匹配，也删掉基线里对应的那一行；门禁会报“基线里有、代码里已经没有”的条目，提醒你删。
- 分类 `reject`、`decide`、`extract` 是 #2 要迁的（10-26 共 169 处）；`format`、`own-text`、`external-text`、`display` 是首版按旧规则登记的其他 95 处。历史分类不能证明符合当前意图／授权规则；改到时逐项核对，只有确属上述技术用途的才可改成对应例外注释，其余按意图／授权匹配迁移，不能靠改标签免审。
- 基线里周期提醒（`recurring-task-intent.ts`）历史记为 `format`：#576 之后的句式命中免确认快速通道仍在判断意图和授权，不符合当前规则，不能继续用 `format` 或 `r1-exempt` 认定合规。本次文档更新不改变产品实现或基线分类，后续迁移按已批准范围执行。

## 不覆盖的

- 从包名导入的（`@allrice/...`），只追相对路径的 `import`；
- 调用一个内部含匹配的函数（例如在新的地方调用现有的 `explicit*Intent`）：门禁只看匹配本身，不跟调用链；
- 只有一个英文词的匹配（`/\bremember\b/i`），以及不含虚词的英文词组（`go ahead`）；
- 回调参数以外的命名函数、`reduce`、运行时拼出来的属性名；
- Swift、Python 等非 JavaScript/TypeScript 源码。

基线只减不增，不通过缩小扫描范围、扩大跳过目录或豁免来放松门禁；改门禁本身（扫描范围、跳过的目录、例外类别、英文词表）同样走 PR 复核。
