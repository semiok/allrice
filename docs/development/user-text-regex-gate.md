# 门禁：不新增“用正则判断用户原话”的代码

MET-210 #2，规则见 MET-220 R1。2026-10-26 加入，是 MET-210 三道“只减不增”门禁的第一道。

## 拦什么

R1：理解用户交给模型；授权靠来源（真人消息）和确认卡；正则只用来放行明确的格式，不能用来拒绝用户。对用户原话做匹配、匹配不上就拒绝、报错或不执行，是要逐步去掉的做法（MET-210 #2），新代码不能再加。

“输入是不是用户原话、匹配不上会不会拒绝”没法静态判断，所以门禁宁多勿少。范围是 `apps/`、`packages/` 的产品代码（不含测试、夹具和构建产物）。“措辞”指中文，或者至少两个英文请求用词、其中一个是虚词（`please`、`don't`、`my`、`the` 这类，见脚本里的 `englishWording`）。下面这些都算一处：

- 含措辞的正则字面量（转义也解开）；`[\u4e00-\u9fa5]` 这类字符范围、`\p{Script=Han}` 表示“任何汉字”，不算措辞；
- `RegExp(...)` / `new RegExp(...)`，模式算出来含措辞；
- 在写正则的声明之外使用一个含措辞的正则（`test`、`exec`、`match`、`replace`、`search`、`split` 等）：给现有的正则加一个新调用方，也是新的一处；
- `includes`、`startsWith`、`endsWith`、`indexOf`、`lastIndexOf`、`match`、`matchAll`、`search` 的参数是措辞；在措辞词表或词典里判断成员、按键查找（`WORDS.includes(text)`、`new Set(WORDS).has(text)`、`TABLE[text]`、`text in TABLE`、`new Map(...).get(text)`）；和措辞做相等比较或 `case`。

名字按作用域解析：同一文件里的常量、相对路径 `import` 进来的常量、迭代出来的元素（`for...of`、`some`/`find`/`map` 等回调的参数、解构、`Object.keys/values/entries`、`Map` 的键、规则表里的字段），以及对象属性和类的静态属性。

现存的 274 处（53 个文件）写在基线 `scripts/user-text-regex-gate.baseline.ts` 里，按“文件 + 所在函数 + 匹配文本”登记，每组写明分类和用途。CI 只拦基线之外新出现的。

## 怎么跑

```bash
pnpm user-text-regex:verify
```

约 4 秒，不需要数据库。默认和 `origin/main` 的合并基准比较基线；`--base <提交>` 指定基准，`--list` 列出每一处的当前行号和状态（基线里的分类、例外类别，或 `NEW`），`--json` 输出全部结果。参数写错时退出码是 2。`pnpm test` 也会跑 `scripts/user-text-regex-gate.test.ts`。

CI 在 `validate` 任务的 `pnpm typecheck` 之后跑这一步，`--base` 是 PR 的基准提交（推到 main 时是推之前的 main）。

## 被拦下怎么办

1. **先改做法**：理解交给模型，模型给结构化参数，服务端校验结构；需要用户点头的走确认卡；真人来源校验（`assertEmployeeChatHumanSource`）保留。做法见 MET-210 #2 和 #576（周期提醒）。
2. **确实不是 R1 的**，在这一处正上方单独一行写例外，理由写在同一行、至少 10 个字，说清楚“没匹配上为什么不会拒绝用户”：

   ```ts
   // r1-exempt(format): 只认“第 N 页”这一种写法，不命中照常交给模型
   const page = /第(\d+)页/u;
   ```

   例外写在包含这一处的语句、属性、类成员或 `case` 的上方；同一行有几处，或者这一处在 `else if (...)` 条件里，就紧挨着写成行内注释：`/* r1-exempt(format): … */ /^第\d+页$/u.test(text)`。类别只有四种：

   | 类别            | 什么时候用                                                                                   |
   | --------------- | -------------------------------------------------------------------------------------------- |
   | `format`        | 只认一种明确写法：命中就放行或取值，不命中照常交给模型或走默认流程，不拒绝、不报错、不跳过   |
   | `own-text`      | 匹配的是系统自己写出的固定文本或标记（含提问卡上系统给的选项），不是用户原话，也不是模型输出 |
   | `external-text` | 匹配的是外部系统写出的固定文案（网页拦截页、第三方报错）；外部给了错误码就用错误码           |
   | `display`       | 只影响展示（高亮、截断、排版），不影响做不做、怎么做                                         |

   一条例外只管一处。写在行尾、写在带花括号的外层函数上、一条管两处、类别不认识、理由太短、下面没有匹配、写在门禁读不到的地方（JSX 里、字符串里、`}` 前面），门禁都会报错。箭头函数只有一个表达式时（`const f = (t) => /…/.test(t)`），写在这个常量上方就算这一处的例外。

   新加的例外不会让 CI 失败，但会列在输出的 “Review under MET-220 R1” 里，在 GitHub 上作为警告标在 PR 对应的行上，复核时按 R1 审。

3. **不要把新代码加进基线。** 基线只减不增：CI 拿 PR 的基线和基准提交的基线做匹配，找不到对应的就失败。能对应上的只有三种：
   - 文件、所在函数、文本都一样；
   - 分类相同、文本相同，文件或所在函数有一个没变（跟着代码搬家）；
   - 分类相同，文件和所在函数都没变（原地改了这条正则）。

   所以每个函数的条数、#2 待迁的条数都不会变多，核对过不算 R1 的条目也不能拿来换一条新的 #2 条目。搬家、原地修改、把分类从 #2 改成不算 R1，都会列进 “Review under MET-220 R1”，并在基线文件上标警告。原地修改要按 R1 审：能迁就迁，不要靠多加几个说法来修“说法没匹配上”的问题。又搬家又改名又改文本的，拆成两个 PR。

## 基线怎么减

- #2 迁移一处后，删掉代码里的匹配，也删掉基线里对应的那一行；门禁会报“基线里有、代码里已经没有”的条目，提醒你删。
- 分类 `reject`、`decide`、`extract` 是 #2 要迁的（10-26 共 177 处）；`format`、`own-text`、`external-text`、`display` 是核对过不算 R1、只因为第一个 PR 不改产品代码才放在基线里的（97 处），以后改到那个文件时可以顺手换成代码里的例外注释。
- 基线里周期提醒（`recurring-task-intent.ts`）记为 `format`：#576 之后，命中句式只是免确认的快速通道，没命中出确认卡，不再拒绝。

## 不覆盖的

- 从包名导入的（`@allrice/...`），只追相对路径的 `import`；
- 调用一个内部含匹配的函数（例如在新的地方调用现有的 `explicit*Intent`）：门禁只看匹配本身，不跟调用链；
- 只有一个英文词的匹配（`/\bremember\b/i`），以及不含虚词的英文词组；
- 回调参数以外的命名函数、`reduce`、运行时拼出来的属性名；
- Swift、Python 等非 JavaScript/TypeScript 源码。

改门禁本身（扫描范围、跳过的目录、例外类别、英文词表）同样走 PR 复核。
